Yes—but there is an important boundary you need to design around:

You cannot guarantee “100% zero visibility” of data in a browser if the browser must receive that data in plaintext and JavaScript must use it.

If a value reaches React as plaintext, a user controlling the browser can ultimately inspect it through DevTools, breakpoints, memory inspection, modified JavaScript, extensions, or an intercepting environment. Encryption in transit does not solve this because TLS terminates at the browser.

What you can build is a system where sensitive data never reaches the browser in plaintext at all, except for the minimum information that absolutely must be displayed/used.

For your Java 21 + Spring Boot + React architecture, I would design it as a server-authoritative, zero-sensitive-client-storage architecture.

OWASP specifically recommends avoiding sensitive information in localStorage, because JavaScript can access it, and recommends HttpOnly cookies for session identifiers.

6. Don't put sensitive information in JWTs

A common mistake is:

{
  "sub": "123",
  "email": "john@example.com",
  "accountNumber": "123456789",
  "role": "ADMIN",
  "salary": 500000
}

Even if signed, the JWT payload is normally readable by whoever possesses it.

A signed JWT means:

"You can't modify this without detection."

It does not mean:

"You can't read this."

Use opaque sessions or keep JWT claims extremely minimal.

For example:

{
  "sub": "user-8f3a",
  "iss": "your-auth-server",
  "exp": 1790000000
}

Better still, if your architecture allows it:

HttpOnly opaque session cookie
        ↓
server-side session

8. But TLS doesn't hide data from the browser

This distinction is extremely important.

Suppose you have:

POST /api/customer

TLS encrypts:

Browser ──────────────── Internet
          encrypted

But when the browser receives the HTTPS response:

{
    "secret": "ABC123"
}

the browser decrypts TLS.

Therefore DevTools can potentially see:

Response:
{
    "secret": "ABC123"
}

So:

TLS protects against network interception.

It does not protect plaintext from the browser itself.

That's why your architecture must minimize what reaches the browser.

13. Browser caching

For sensitive API responses:

Cache-Control: no-store

This is extremely important.

OWASP explicitly recommends Cache-Control: no-store for sensitive responses because TLS only protects data while it is in transit; it does not prevent the browser or intermediary from caching the response.

You can also consider:

Pragma: no-cache
Expires: 0

for legacy compatibility.

And at logout:

Clear-Site-Data: "cache", "cookies", "storage"

where appropriate.

29. Searchable encrypted data

There is a catch with encryption.

Suppose:

+

expose database entities
log entire request objects
log entire response objects
put credentials into localStorage
hardcode encryption keys
SECURITY DECISION RULE

Whenever there are two implementation choices, prefer the one that results in:

less data
+
less client exposure
+
less persistence
+
less privilege
+
stronger server-side authorization
+
stronger cryptography
+
less telemetry exposure
OUTPUT REQUIREMENTS

When implementing a security feature, explain:

What vulnerability/risk exists.
What architectural change fixes it.
Which files are modified.
What security controls are added.
What data is no longer exposed.
How the implementation is tested.
What limitations remain.

Never claim absolute security.

Use precise language such as:

prevents
mitigates
reduces exposure
does not protect against

rather than:

100% secure
impossible to hack
DevTools-proof
FINAL SECURITY PRINCIPLE

The application must be designed so that:

Sensitive information is processed as close to the trusted backend boundary as possible, is encrypted when stored, is protected in transit, is never unnecessarily sent to the browser, is never unnecessarily persisted, is never logged, and is never trusted when supplied by the client.

One recommendation before you run this

For a real project, don't give Cursor only the implementation prompt and tell it "do everything." The safest workflow is:

Cursor
  ↓
AUDIT ONLY
  ↓
Security report + data-flow map
  ↓
You review architecture
  ↓
IMPLEMENT
  ↓
Tests
  ↓
Security regression audit

That prevents an agent from making a large security-sensitive rewrite based on incorrect assumptions about your existing authentication, APIs, database schema, deployment, or business requirements.

If your project is substantial, I would also split the implementation into 5 Cursor tasks—backend security, encryption/KMS, React/browser isolation, logging/telemetry, and security testing—rather than one enormous agent task. That generally gives you much better control over security-critical changes.
